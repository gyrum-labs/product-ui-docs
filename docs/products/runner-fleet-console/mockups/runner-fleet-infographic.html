About this page

This is the front door: the fleet as one picture, and the three numbers that decide whether anything is moving. Runners is how many the registry knows; busy is how many are holding a job right now. Running jobs and queued jobs are the work in flight and the work waiting for a runner to pick it up.

The heavy slot is the repo's single heavy-CI lane. Every heavy devtools run shares it, so one run at a time validates against main — and one long-held slot starves every other pull request. The queue depth is the train's service order, and the head is the pull request it serves next. Train is the state of that read.

About this page

Every runner the fleet's registry knows about, sorted so the ones doing work come first. Each row gives the runner's name and host, its class and lane, whether it is busy, the job it is holding, the labels that decide which work it may take, and when the registry last heard from it.

The two objectives

Every row carries both. Green is inside the target, amber is past half of it, red is past it.

Time to be seen
how long a pull request waited before the fleet picked it up — target: under 24 hours. Measured from when the pull request opened to the moment it joined the train.
Time to process
how long it has waited in the train since — target: under an hour. Measured from the enqueue record to now, or to the moment it was merged.

A pull request outside the train has no enqueue record, so it has no time to be seen or to process — those rows read as —.

How these buckets are decided

The board's phase vocabulary lives in the warp service, so these are derived here from what can be measured: the pull request's own state, its check rollup, its review decision, the train's labels, the owning ticket's status, and the heavy gate's own run list — the last one, because the rollup alone cannot see the heavy lane.

About this page

Every pull request, bucketed by how far it has got. The board's own phase vocabulary lives in the warp service, so these buckets are derived here from what can be measured: the pull request's state, its check rollup, its review decision, the train's labels and the owning ticket's status.

Waiting is open, not green and nobody is holding it. Waiting fixed has changes requested or a conflict on the train. In testing has the heavy gate running on its current head. Passed is green and approved, waiting its turn. Waiting for deployment is merged with the delivery tail outstanding. Deployed is merged and delivered within a day; done is merged and settled.

The Heavy column is the one that matters most, and it exists because the check rollup cannot be trusted on its own. The heavy gate is a single-slot workflow that fires only when the train marks its one current candidate ready for review, so it has no check run at all until a runner picks it up, and a pull request whose head moved after that transition never gets one. The light lane is green in seconds, so the rollup reads SUCCESS and the pull request looks tested when it has not been. The column reads the heavy gate's own run list instead: not run means the gate has never run on that head, queued means it is waiting for the single slot, running means it is on a runner now, and failed means the gate ran and went red.

Reading it
the sizes of the first three buckets are the real signal: a long "waiting" bucket means the fleet is not picking work up, and a "passed" bucket full of not run means the gate has not been reached rather than that the work is sound

Five ways to see the same fleet

Every panel is driven by the same live payload: how many runners are busy, how many jobs are running or queued, and how long each has been at it.

About this page

Five ways of drawing the same fleet, so you can see which one carries the truth best. A bowl of fish: one fish per busy runner, the water level rising with utilisation. Rain into a basin: one drop per job, running and queued. Stacking blocks: one column per runner, blue for the heavy lane. A constellation: one star per runner and one line per job. Radar: a sweep over the pool with a blip for each busy runner.

Everything moves. Each panel runs a small swarm: the bodies repel one another, are pulled toward an anchor, wander a little and are damped by drag, so nothing sits still and the arrangement is never exactly the same twice.

Reading it
the panels are alternate readings of one payload — use whichever makes the state obvious to the person you are showing it to

The floorplan

One room per state. The corridor is the train's service order. When a pull request's state changes, it walks to the next room — the walk is the change.

About this page

A floorplan of the delivery pipeline. One room per state, and the corridor is the train's service order. Every pull request stands in the room of its current state.

When a pull request's state changes, the figure walks: out of its room, along the corridor, into the next one. The walk is the change — nothing teleports, so a movement you can follow is a state transition you can read. The ring around a figure flashes when its checks or its review change, which is the other property the state is made of.

Reading it
figures still walking are pull requests mid-transition; a room emptying faster than it fills is work moving forward
